## 2. 사용자 요청과 작업 방식

대상은 **`littlebit0/DailyCalendar`**다. Promonts와 연결하지 않는다. 사용자는 버그 탐지, 코드 리뷰, 성능 분석, 최적화 필요사항 및 구체적인 수정 방향을 **파일·코드 한 줄도 분석 대상에서 빼지 않고** 검토해 달라고 요청했다. 실제 발견은 원인별 GitHub 이슈로 작성하고 중복이면 기존 이슈를 보강하는 방식이다.

우선순위는 제목의 High/Critical/P1 같은 글자가 아니라 **`priority: high`, `priority: medium` 등의 라벨**로 관리한다. 기존 `bug`, `enhancement`, `documentation` 및 다른 라벨은 보존한다. 발견·등록을 구현 완료로 취급하지 않으며, 이슈가 닫혔다는 사실만으로 실제 기능 정상이나 회귀 검증 완료를 추정하지 않는다.

장시간 작업 중 여러 차례 '생각 실패'로 응답이 중단됐다. 실제 내부 실패 원인은 확인하지 못했다. 이후 체크포인트를 외부 파일로 보존하며 계속했다. 사용자는 '이슈 한 건마다/2분마다 중단'을 원한 것이 아니라 **약 30분의 연속 작업 단위**를 원했다. 30분은 자동화 예약이 아니며 정확한 처리시간 보장이 아니다. 진행 중에는 간헐적으로 확인한 결과를 출력하고, 종료 전에 파일·행·커밋·이슈 번호·검증 수준·다음 지점을 저장한다. 최종 응답 뒤 자동으로 계속 작업한다고 말하지 않는다.

## 5. 전체 이슈 인계 범위

**#93–#170의 78개 번호를 전체 색인에 빠짐없이 넣었다.** #105–#108, #149–#153의 **9개는 별도 연계 항목**으로 표시했다. 나머지 69개는 이 대화에서 감사·등록 대상으로 추적한 항목이다. '78개를 전부 단독으로 새로 발견·생성했다'는 뜻이 아니다.

각 이슈의 정식 본문에는 기준 커밋, 파일·함수, 문제 조건, 수정 방향, 확인한 것과 미확인한 것, 회귀 조건이 있다. 색인은 빠른 진입용이며 본문과 댓글을 대체하지 않는다. 이 인계에서는 기존 이슈 상태·라벨을 전수 변경하거나 신규 버그를 등록하지 않는다. 과거 등록 당시 라벨을 현재 값으로 가정하지 않는다. 예를 들어 #143은 인계 확인 시 `priority: critical`이므로 과거 추정치로 되돌리지 않는다.

기존 배경 요구도 보존한다. #63은 대학 홈페이지의 학사일정이고 #65는 LMS 가져오기다. #87은 학사/LMS 동기화·보존·완료 연계·동영상 및 이러닝 출석 일정 요구, #88은 브라우저 로그인 뒤 세션 만료와 일정 삭제, #89는 LMS 일정 분류, #90은 초기 로딩·갱신 실패, #91은 안전한 자동 오류 보고의 기존 상위 이슈다. 이들을 전부 오늘 새로 만든 이슈로 계산하지 않는다. 대화 초반의 종료 이슈 포함 `bug`/`enhancement` 라벨 적용 기록도 현재 우선순위·완료 검증의 대체 근거가 아니다.

## 6. 반드시 이어받을 정정·보강

### #87: 잘못 추가한 원인 설명 철회

[정정 댓글 6144779199](https://github.com/littlebit0/DailyCalendar/issues/87#issuecomment-6144779199)이 우선한다. `LmsSyncService._apply`의 prepare 반환에 completed가 없다는 이유만으로 기존 일정 자동 완료가 누락된다고 했으나, 실제로 `EventCommandService.importBatch`의 **최종 트랜잭션 resolver**가 값을 계산한다.

```dart
completed: preserveLmsSource
    ? latest.completed
    : latest.lms?.manuallyCompleted == true
    ? true
    : source.lms?.sourceCompleted ?? latest.completed,
```

원래 사용자 신고와 네 가지 요구는 유지한다. 이 정정은 실제 LMS·기기 문제가 모두 해결됐다는 뜻이 아니다. 생성→전달→최종 저장→표시→타 기기 복원까지 확인하기 전에 중간 객체의 누락만으로 다시 이슈를 만들지 않는다.

## 7. 사용자 요청 #158–#161의 정확한 의미

**#158:** macOS의 자동 로그인은 사용자가 정상이라고 보고했다. **iOS에서만 저장 계정 자동 로그인 적용이 안 된다**는 신고다. 수동 로그인이나 모든 플랫폼도 실패한다고 확대하지 않는다. headless host 준비와 정확한 cookie-store/WebView 결속을 추적했지만 iOS window 접근 차이를 실제 원인으로 확정하지 않았다. 결속 조건을 느슨하게 해 다른 WebView에 암호를 넣는 방식은 금지한다.

**#159:** ID·비밀번호를 저장한 뒤 바로 재로그인하는 버튼과 입력 중 비밀번호 표시/숨김이다. 비밀번호 확인용 두 번째 입력란을 새로 만들거나 매번 같은 정보를 다시 저장하도록 요구하는 뜻이 아니다.

**#160:** 보이는 표기를 정확히 `ID`로 바꾸고, ID/password의 의미 힌트와 로그인 폼 구조로 Apple 암호 자동완성을 지원한다. 사용자가 Apple 암호에서 선택할 수 있는 Coursemos·학교 저장 계정 재사용이 대상이다. Coursemos 앱 내부의 비공개 키체인을 Daily가 임의로 읽는 방식이 아니며, 학교 도메인의 앱 연결 승인도 Daily가 혼자 부여할 수 없다.

**#161:** 일정 수가 적은 분류 박스 아래를 옆의 긴 박스 높이만큼 비우지 않도록 열별 콘텐츠 높이 배치를 검토한다. 분류 순서, 완료 조작, 스크롤, 접근성, 현재 열 수를 유지한다.

#158 관련 Mac CI의 40개 session 검사는 bridge/headless/controller 대역을 사용한다. 그 테스트 파일에는 실제 `loginAutomatically` 직접 호출이 없고 다른 테스트도 해당 메서드를 override한다. **40개 통과를 실제 iOS 자동 로그인 성공으로 보고하지 않는다.**

## 10. 검증 종류와 한계

- **정적 추적:** 실제 소스의 UI→서비스→최종 저장→후속 작업·표시 연결. 코드 경로 확인이지 실기기 재현이 아니다.
- **Python 모델:** Dart/Swift의 조건·날짜·상태 전이를 옮긴 모델. 수정된 저장소를 자동으로 실행하지 않는다.
- **발췌한 함수 실행:** Python 수신기/helper 등의 일부 실제 함수와 대역·합성 입력을 사용. 서버 전체/운영 전송이 아니다.
- **SQLite 실험:** 실제 SQLite이지만 합성 과거 스키마 또는 최소 스키마·임시 파일. 앱의 실제 Drift 생성 SQL·사용자 DB 검증으로 바꾸지 않는다.
- **Swift 발췌:** Linux Foundation과 대역으로 일부 함수를 검사. iOS/macOS WebView·WidgetKit·AlarmKit·Keychain 실행이 아니다.
- **공식 계약 대조:** 외부 API·프레임워크 문서와 코드 비교. 다음 담당자가 의존성을 바꾸면 해당 버전 문서도 재확인한다.

이번 인계 ZIP에 실행 영수증과 함께 보존된 구간별 격리 스크립트는 **7+5+3=15개**다. 이는 오늘 모든 실행 모델의 총수가 아니라 회수한 세 구간의 숫자다. 등록 차단 모델 1개도 기존 묶음 안에 있으며 실행·등록을 다시 시도하지 않았다. 인계 작성 중에는 기존 probe를 재실행하지 않고 파일·기록을 정리했다.

**수행하지 않은 검증:** Flutter/Dart 전체 또는 선택 테스트 실행, 플랫폼 빌드, 사용자 앱 실행·설치, 실제 WebView/로그인·학사 계정·Drive 동기화, 운영 분석 서버·실제 제보, 사용자 PIN·암호 저장소, 실제 기기의 CPU/메모리/FPS/알림 도착. 이 감사 환경에는 Dart/Flutter SDK가 확인되지 않았고 직접 다운로드는 DNS 실패 기록이 있다. 현재 다른 담당자 환경까지 같다고 가정하지 말고 가용 도구를 확인한다.

모델 결과가 버그 경로를 보여도 수정 검증에는 실제 프로젝트 회귀 테스트가 필요하다. 모델을 그대로 다시 실행해 성공했다고 제품 수정 완료로 보고하지 않는다. 과거 run_probes.py는 원래 스크립트 폴더에서 사용하며 합성/임시 데이터 범위를 먼저 읽는다.

## 11. 다음 담당자의 재개 절차

1. 현재 HEAD·브랜치·미커밋 변경을 확인하고 기록 기준과 compare한다. 다른 담당자의 dirty diff·앱 설치·계정을 초기화하지 않는다.
2. 최신 인계와 이슈 댓글부터 읽어 #87처럼 철회된 진단을 제거한다. 신규 등록 전 기존 open/closed 이슈와 같은 원인을 대조한다.
3. 실제 전체 tree를 누락 없이 확보한다. 큰 응답은 디렉터리/하위 tree로 나누고 truncation을 검사한다. 경로·blob·읽은 구간·EOF·정적/실행 검증을 별도 관리한다.
4. 회수 원장의 blob과 같은 파일은 전체를 무조건 다시 읽지 말고 미검토 구간·호출 연결부터 확장한다. 증거가 불완전한 초반 파일은 미검토 가능성을 명시하고 필요한 범위를 재확인한다.

6. **그다음:** `test/core/lms/lms_credentials_store_test.dart` 및 남은 테스트. 이미 읽은 파서 3개·퀴즈 fixture·Coursemos HTML 7개·owner/persistence 테스트는 마지막 원장과 대조한다.

이전 '[skip ci] 또는 45개 선택 테스트를 전체 CI 해결로 보고'했던 별도 작업의 철회·재발 방지 기록도 보존한다. 선택한 테스트, mock 통과, 문서의 보고를 전체 CI·실기기·대학 지원 완료로 확대하지 않는다. 인계 문서 게시에 따라 별도 자동 CI가 실행돼도 그 결과는 새로 확인하기 전까지 성공으로 보고하지 않는다.

## 14. 전달 묶음과 확인 가능한 증거

전달 ZIP의 시작 파일은 `HANDOFF.md`다. `ISSUE_REGISTER.md/json`은 78개 번호 색인, `FILE_REVIEW_LEDGER.md`와 `RECOVERED_COVERAGE.json`은 회수 원장 통합, `checkpoints/`는 여섯 인계 문서다. `evidence/`에는 기존 네 ZIP에서 복원한 원본 범위·영수증·스크립트·결과·로그가 있다. `SHA256SUMS.txt`로 새 묶음의 파일 바이트를 확인할 수 있다.

**자료의 권위 순서:** 사용자 최신 지시 → 현재 코드·정식 이슈/댓글 → 해당 커밋의 실제 검증 영수증 → 체크포인트 요약. 이전 오류 설명을 정정 댓글보다 우선하지 않는다. 대화의 `/response/turn...` 참조는 추적용이며 다음 담당자의 런타임에서 재사용 가능한 파일 경로로 간주하지 않는다.

이번 인계에서는 기존 `AGENT_MEMORY.md`의 다른 담당자 기록을 대체·정리하지 않는다. 전용 감사 문서와 전체 이슈 색인을 새로 남기며, 제품 코드와 원래 이슈 본문·상태를 변경하지 않는다. 실제 게시한 문서 커밋·URL·로컬 파일 해시는 `TRANSFER_RECEIPT.json`과 최종 전달 메시지에 기록한다.
